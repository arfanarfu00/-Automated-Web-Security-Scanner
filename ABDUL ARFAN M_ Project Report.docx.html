1. Abstract

This project presents the Automated Web Security Scanner, a web-based cybersecurity dashboard that audits HTTP security response headers and Cross-Origin Resource Sharing (CORS) configurations of any user-specified website. Built entirely in a single Python file using the Streamlit framework, the tool performs a fully passive inspection — sending one standard HTTP GET request and analysing the headers returned — without exploiting vulnerabilities, storing credentials, or crawling linked pages.

The scanner produces a structured report covering six critical security headers, four CORS headers, an educational security score (0–100), a categorised threats table, matched remediation recommendations, and downloadable JSON and CSV reports. The project is designed to be beginner-friendly, reproducible, and safe for use in educational environments.

2. Project Objectives

  1. Build a functional web-based tool that scans HTTP response headers for security misconfigurations.
  2. Detect missing or weak implementations of six industry-standard security headers.
  3. Analyse CORS configuration headers and flag potentially unsafe combinations.
  4. Present results through a dark-themed cybersecurity dashboard with metric cards, bar charts, and filterable tables.
  5. Generate a documented, heuristic-based security score with a transparent scoring formula.
  6. Provide a dedicated Threats Detected table and a matched Recommended Solutions section.
  7. Export full scan reports in both JSON and CSV formats, including threats and solutions.
  8. Demonstrate responsible disclosure principles: no exploitation, no credential storage, passive analysis only.

3. Background & Motivation

HTTP response headers are one of the most accessible and commonly misconfigured aspects of web server security. Headers such as Strict-Transport-Security, Content-Security-Policy, and X-Frame-Options are free to implement, require no code changes to the application itself, and provide measurable defence against a range of well-documented attacks — including Cross-Site Scripting (XSS), clickjacking, protocol-downgrade interception, and cross-origin data theft via CORS misconfiguration.

Despite this, surveys consistently show that a significant proportion of public websites — including institutional and commercial sites — are missing one or more of these headers. This project aims to make that gap visible and actionable for developers, students, and security practitioners without requiring specialised tooling or network access.

Scope constraint: The scanner only audits the single URL entered by the user. It does not crawl links, interact with login forms, inject payloads, or access any resource beyond the initial HTTP GET response.

5. System Architecture

The entire application is contained in a single file, app.py, organised into clearly separated layers:

5.1 Configuration Layer

st.set_page_config() and the DARK_CSS constant establish the page title, icon, wide layout, and complete dark-theme styling. The SECURITY_HEADERS dictionary defines the six audited headers with their risk level, explanation, and remediation text. The _SOLUTION_LOOKUP dictionary maps each of 14 possible threat names to a full solution entry (why it matters, recommended fix, example configuration, verification steps).

5.2 Scanning Layer

scan_website(url) is the single entry point for all network activity. It calls requests.get() with a 10-second timeout, a custom User-Agent string, and redirect following enabled. All seven exception types raised by the Requests library are handled individually and returned as user-friendly error messages. No second request is ever made.

5.3 Analysis Layer

Five analysis functions process the response headers:

  • _audit_headers() — checks presence and basic validity of the six security headers.
  • _header_needs_review() — applies heuristics (e.g. short HSTS max-age, unsafe-inline in CSP) to distinguish strong from weak implementations.
  • _audit_cors() — reads four CORS response headers and flags wildcard origins, credential misconfigurations, and dangerous allowed methods.
  • _build_threats() — converts findings into the Threats Detected representation with context-aware logic (e.g. HSTS on HTTP is Informational, not High).
  • _build_solutions() — matches each threat to its corresponding solution from the lookup table, deduplicating by threat name.

5.4 Scoring Layer

_compute_score() implements the documented scoring formula (see Section 7). _score_colour() returns a colour code for the score display.

5.5 Report Layer

_build_json_report() and _build_csv_report() serialise all scan data — including threats and solutions — entirely in memory using Python's standard library. No files are written to disk.

5.6 UI Layer

main() orchestrates all dashboard sections. Results are stored in st.session_state so that filter changes, expander toggles, or section switches never trigger a new HTTP request. Rendering helpers (_render_metric_card(), _badge(), _sev_span(), _render_threats_section(), _render_solutions_section()) keep the HTML generation contained and reusable.

6. Feature Set

6.1 Dashboard Overview

  • Dark-themed cybersecurity dashboard with custom CSS injected via st.markdown(unsafe_allow_html=True).
  • Responsible-use disclaimer displayed prominently above the scan input.
  • URL text input with automatic scheme normalisation (adds https:// if omitted).
  • Four metric cards: Headers Checked · Missing Headers · CORS Warnings · Total Findings.
  • Scan metadata: target URL, HTTP status code (colour-coded), response time in milliseconds.

6.2 Security Score

  • Score displayed as a large number (0–100) with a colour-coded progress bar.
  • Descriptive rating: Good (≥ 85) · Fair (≥ 65) · Poor (≥ 40) · Critical (< 40).
  • Scoring formula shown inline on the dashboard (see Section 7 for full formula).
  • Clearly labelled as an educational heuristic, not a certified assessment.

6.3 Visual Analysis

  • Bar chart: findings grouped by severity level (High, Medium, Low, Informational).
  • Bar chart: security headers grouped by status (Present, Missing, Needs Review).
  • Both charts use Streamlit's native st.bar_chart() with colour overrides.

6.6 Security Findings Table

  • Unified table combining header and CORS findings: Title, Category, Severity, Explanation, Recommended Fix.
  • Dropdown filter by Severity (High / Medium / Low / Informational / All).
  • Dropdown filter by Category (Security Header / CORS Configuration / All).
  • Expandable detailed view with per-finding styled cards.
  • Filters operate entirely on cached session-state data — zero additional HTTP requests.

6.7 Threats Detected Section

  • Dedicated section with a 5-column summary table (Threat Name, Category, Affected, Observed, Risk Level).
  • Context-aware logic: HSTS missing on an HTTP URL → Informational (not High).
  • Expandable detail cards per threat with full explanation and explicit acknowledgement of evidence limitations.
  • Friendly "no issues" message when all checks pass, noting that header analysis is not exhaustive.

6.8 Recommended Solutions Section

  • One solution card per detected threat, matched by threat name from _SOLUTION_LOOKUP.
  • Each card contains: Why it matters · Recommended solution · Example configuration (monospace block covering Apache, Nginx, and Node.js where applicable) · Numbered verification steps.
  • 14 pre-defined solution entries covering every possible threat type the scanner can produce.
  • No duplicates: the same threat type is never shown twice even if triggered by multiple findings.

6.9 Downloadable Reports

  • JSON report — structured document with scan_info, security_score, header_findings, cors_findings, security_findings, threats_detected, and recommended_solutions.
  • CSV report — metadata row, security findings, a Threats Detected section, and a Recommended Solutions section, all generated in memory via Python's io.StringIO.
  • Both files are named with the scan timestamp and offered via Streamlit's st.download_button().

9. Security & Ethical Considerations

9.1 What the tool does NOT do

  • Does not send forged or manipulated HTTP headers (no Origin spoofing).
  • Does not follow links or crawl pages beyond the single entered URL.
  • Does not attempt authentication bypass, SQL injection, or any form of exploitation.
  • Does not store cookies, session tokens, passwords, or user-identifiable data.
  • Does not write files to disk (reports are generated entirely in memory).
  • Does not contact external services, APIs, or third-party analytics.

9.2 Responsible-use design choices

  • A prominent disclaimer is displayed before every scan reminding users to only scan sites they own or have permission to test.
  • Every threat explanation explicitly states the limitations of the evidence and avoids claiming confirmed vulnerability.
  • The security score is labelled as an educational heuristic on both the dashboard and in all exported reports.
  • The User-Agent header sent with each request identifies the tool: AutoWebSecScanner/1.0 (educational).
Legal notice: Scanning websites without the owner's explicit permission may violate computer misuse laws in many jurisdictions. This tool is intended for educational use on websites you own or are authorised to test.

10. Installation & Usage

10.1 Prerequisites

  • Python 3.8 or later installed and available on the system PATH.
  • pip package manager (included with Python).
  • Internet connection (for scanning live websites).

10.2 Install dependencies

pip install streamlit pandas requests

10.3 Run the application

streamlit run app.py

Streamlit will print a local URL (typically http://localhost:8501). Open it in any modern browser. No additional configuration is required.

10.4 Usage steps

  1. Enter a website URL in the text box (e.g. https://example.com).
  2. Click Scan Website. The scan completes in under 10 seconds.
  3. Review the metric cards, security score, and visual charts.
  4. Expand the Security Header Audit and CORS Analysis sections.
  5. Review the Threats Detected table and expand individual threat cards.
  6. Read the Recommended Solutions for each detected threat.
  7. Use the severity and category dropdowns to filter findings.
  8. Download the JSON or CSV report using the buttons at the bottom of the page.

12. Limitations

  • Single endpoint only: The scanner audits one HTTP response. Headers may differ between pages on the same site.
  • No JavaScript execution: Headers set via meta tags or JavaScript are not detected.
  • CDN/proxy layers: Security headers may be injected by a CDN (e.g. Cloudflare) not visible at the application layer.
  • CORS without an Origin header: The scanner reads CORS headers returned in a plain GET response. Some servers only return CORS headers in response to a preflight or an explicit Origin request header; those cases are not tested.
  • No dynamic analysis: XSS, SQL injection, authentication flaws, and business-logic vulnerabilities cannot be detected from response headers alone.
  • Heuristic score: The score is not calibrated against any external benchmark and should not be cited as a compliance or risk rating.

13. Future Improvements

  • Add support for scanning multiple pages from a provided sitemap or URL list.
  • Include TLS/SSL certificate checks (expiry, weak cipher suites, certificate chain).
  • Add a preflight CORS check by optionally sending an OPTIONS request with a test Origin header (with explicit user consent).
  • Integrate with the OWASP ZAP API for deeper passive scanning.
  • Add a history view to compare scan results across time using a local SQLite database.
  • Support subdomain enumeration or robots.txt parsing for scope discovery (with user consent).

14. Conclusion

The Automated Web Security Scanner successfully demonstrates the practical application of Python, Streamlit, and Pandas to a real-world cybersecurity problem. It provides a complete, self-contained educational tool that teaches the significance of HTTP security headers and CORS configuration through interactive scanning, structured reporting, and clear remediation guidance.

The project was implemented entirely within a single app.py file of 1,904 lines, passes all syntax checks, and all core functions pass functional smoke tests. It adheres to responsible disclosure principles by performing only passive header analysis and making no attempt to exploit, authenticate to, or crawl the target site.

The tool is ready for submission and demonstration as a standalone cybersecurity bootcamp project.
